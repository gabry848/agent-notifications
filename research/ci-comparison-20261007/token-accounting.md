# Token accounting for the completed CI coding trials

This is a read-only re-analysis of the existing October 7–8, 2026 evidence. It includes the five complete correct measured pairs in each workload, excludes calibration, and checks all 405 measured provider responses against the primary metrics. No new model workload was run.

## Percentage bases

Each paired change is `100 × (notifications − polling) / polling`. The headline is the median of those five percentages. The aggregate change instead divides the difference between the summed mode totals by the summed polling total. These statistics answer different questions; neither is a fixed overhead for every notification or every task.

For Notes, the pair at the median percentage is p3: **229,712 → 321,792**, or **+92,080 (+40.1%)**. The sum over all five Notes pairs is **1,670,035 → 1,844,553**, or **+174,518 (+10.4%)**. ## Notes p3: where the extra tokens are counted

| Component | Polling | Notifications | Difference | Share of the +92,080 difference |
|---|---:|---:|---:|---:|
| Cached input | 170,368 | 246,528 | +76,160 | 82.7% |
| Uncached input | 50,725 | 66,022 | +15,297 | 16.6% |
| Output | 8,619 | 9,242 | +623 | 0.7% |
| Total | 229,712 | 321,792 | +92,080 | 100.0% |

Input accounts for 91,457 (99.3%) of the increase; output accounts for only 623 (0.7%). Both modes made 20 model requests. Mean input per request was 11,054.7 tokens for polling versus 15,627.5 for notifications. This measures repeated full-context input across requests, not unique text generated by the agent.

Across all five Notes pairs, cached input was 85.5% of polling input and 86.2% of notification input. Cache reuse remained high; cached tokens are still included in the cumulative total. The aggregate uncached input was 234,805 → 247,728 (+5.5%), whereas output was 53,982 → 53,785 (−0.4%). No monetary cost can be inferred from the total-token percentage alone.

## Verified retention mechanism and attribution limit

The [frozen journal implementation](../notes-mcp-ci-20261007/inputs/v3/runtime/src/notification-context.mjs) preserves exact prior notification snapshots at their original conversation anchors so later requests can keep a stable cache prefix. The adapter records one new snapshot per context preparation. While a CI result remains active, it can occur in several snapshots; dismissal removes it from new active snapshots but does not delete already delivered history.

The [Notes p3 notification trace](../notes-mcp-ci-20261007/runs/measured-p3-N-a1/notifications.jsonl) records 20 context preparations, with archived-snapshot counts growing from 0 to 19. Seven notifications arrived. The final request retained all 19 earlier snapshots even though its new active snapshot was empty. The current blocks total 22,111 characters; including their repeated retention across the 20 requests yields 248,167 projected block-character appearances. These are character counts, not tokenizer estimates or billable usage.

The [notification-mode provider/tool trace](../notes-mcp-ci-20261007/runs/measured-p3-N-a1/trace.jsonl) reports 29 tool executions, versus 23 in the [polling trace](../notes-mcp-ci-20261007/runs/measured-p3-PA-a1/trace.jsonl). These include different CI submissions, edits, waits and notification cleanup. Ordinary code, test output and tool history also accumulate in later requests. The last input was 29,796 tokens with notifications versus 19,810 with polling.

Retention directly explains a mechanism that adds context. The observed full-run difference also includes different agent paths; the study has no matched ablation that removes only the notification text while preserving the same actions. It therefore cannot attribute an exact portion of the +92,080 tokens solely to notifications, or establish a universal +40% penalty.

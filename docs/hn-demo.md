# Demo: CI results while the agent keeps working

Run a tiny checkout with an intentional shipping bug. While Pi writes and tests an independent receipt formatter, a local worker tests the shipping code and publishes its result into Pi's next model request. The agent can then inspect the failure and fix it.

**Real tests, simulated queue delay.** This is a demonstration of delivery and task adjustment, not a speed benchmark or a live GitHub Actions integration. [Five-minute setup](quickstart.md) · [Limits](limitations.md) · [Launch preparation](hn-launch.md).

## Start the demo

Requires Node.js 24+ and an installed, authenticated Pi. From this repository:

```sh
node demo/ci.mjs launch
```

The launcher creates a fresh directory under your system's temporary folder, copies the fixture, and starts Pi with only this extension. It submits the initial prompt automatically, so Pi reads `.demo/task.txt` and begins the receipt task without manual input. Once the notification receiver is ready, it also starts the local CI worker automatically. It uses your configured provider and model; model requests have their normal usage or billing. No repository dependency installation is needed. The local receiver chooses a free port, avoiding conflicts with another Pi session.

Keep Pi open while CI runs. No second command is needed for the initial job. The launcher prints the workspace and delivery-log path, and keeps the temporary workspace after exit so you can inspect the result. Worker output goes to `.demo/ci-console.log` to avoid disrupting Pi's terminal UI. To watch delivery in another terminal, use your actual printed workspace:

```sh
tail -f /path/to/demo-workspace/.demo/ci-console.log
```

The worker captures the shipping files and destination session, waits eight seconds to simulate a CI queue, then runs `node --test shipping.test.mjs` on that snapshot. It saves the real output and sends the conclusion, run ID, source hash and log path to `POST /notify`. The initial snapshot should fail at **“orders at $50 qualify for free shipping”**.

Read the delivery log's `CI failure` or `CI success` line for the test conclusion. `HTTP 201` confirms persistence, not that the model has seen or acted on the result. The launcher prints a delivery summary after Pi exits. If Pi exits before delivery, the pending job is cancelled; startup and worker errors are saved in the delivery log.

## What to capture

Aim for a 45–90-second clip, using these moments as a recording checklist. Actual model timing varies.

| Moment | What the viewer should see |
|---|---|
| Start | Pi begins writing the receipt formatter; the local CI job starts automatically. |
| Independent work | Pi edits or tests receipt code while the shipping result is pending. |
| Delivery | The delivery log reports the real failure and HTTP 201. At a later model request, Pi acknowledges the failure without a CI status retrieval call. |
| Reaction | Pi opens the saved log, compares the tested snapshot with current source and fixes the applicable boundary bug. |
| Verification | Both shipping and receipt tests pass; Pi dismisses the specific event and explains the change. |

Keep the command and the **simulated queue delay** label visible. If you trim inactive footage, label the cut. Opening the test log is a separate inspection action; the extension only removes the need to retrieve the arrival/status.

If the agent finishes before the event arrives, send a normal prompt such as **“Continue with any relevant CI result received.”** Identify this as an idle-backlog demonstration, rather than claiming an automatic wake-up. Never assume delivery alone guarantees the model's reaction.

## Inspect and repeat

In Terminal B, change to the printed workspace and verify the agent's work:

```sh
node --test shipping.test.mjs receipt.test.mjs
```

Optionally run the printed repeat command to publish a fresh result for the fixed shipping source:

```sh
node /path/to/pi-notifications/demo/ci.mjs ci /path/to/demo-workspace --delay 0
```

If Pi is idle, another user prompt is required to expose it.

Each job preserves `.demo/runs/<run-id>/snapshot/`, `test.log` and `result.json`. Pi's extension records receive/context/dismiss activity in `.demo/runtime.jsonl`. These local files can support inspection of delivery; they do not record a video or establish model understanding. Receipt output is generated by the agent, not supplied as a successful pre-recorded run.

Run `node demo/ci.mjs launch` again for a clean fixture. Exit Pi before deleting a temporary workspace. The fixture intentionally contains a failing test; it is separate from the repository's test suite.

## Offline verification

With the tested Pi version installed, these checks need no provider authentication or model requests:

```sh
npm run test:demo
npm run test:pi
```

The demo checks exercise automatic task submission to Pi, receiver-readiness handling, job cancellation, real snapshot tests, HTTP delivery, unchanged destination across a session switch, and a fresh success result after a fix. They also start the actual launcher and Pi receiver from a copy without `node_modules`, and verify that launch alone delivers a real CI failure. The startup check intercepts Pi's input before inference; the separate Pi RPC check verifies session routing and SQLite restart behavior without calling a provider. Neither substitutes for recording a live model's task and reaction. The launcher integration checks use a POSIX shell on macOS/Linux.
